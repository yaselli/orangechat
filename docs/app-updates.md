# 版本号与应用内更新

本次发布版本为正式版 `2.3.6`、Debug `2.3.6-debug.1`，Android `versionCode` 均为 `171`。是否已公开以 GitHub Releases 为准。`2.3.0 / 165` 是本项目更新源的首个版本。后续每次发包都递增 versionCode；正式版改 defaultConfig.versionName，同一基础版本内追加 Debug 更新时，同时调整 versionNameSuffix 与 VERSION_NAME 字段中的 debug 序号。

同一份源代码分别通过 Build Stable Release APK、Build Personal APK 构建。拍一拍、消息贴表情、记忆、MCP 等功能共用代码；两种包只在包名、既有签名配置及测试诊断展示上区分。两套应用的数据相互独立。

## 用户体验

- 启动聊天后，开启“更新提醒”的用户在有新版本时看到弹窗，可下载、稍后或忽略该版本。切换聊天窗口不会反复弹出；“稍后”在下次启动进程时可以再提醒。
- 设置 → 关于 → 检查更新可手动检查，不受“忽略此版本”影响。
- 自动检查失败时静默，手动检查失败时提示；成功结果在进程内缓存一小时，失败缓存两分钟，手动检查可立即重试。
- 正式版只接受正式 Release，Debug 只接受 `-debug.N` 的预发布版本；同时匹配 Android versionCode 和设备 ABI，不下载其他渠道或架构的包。
- 新下载流程（自 2.3.5 起）：点击“下载并安装”后在弹窗显示进度、已下载体积和速度；可收起继续下载或暂停。使用应用自身的 HTTP 客户端和 WorkManager 前台任务，不再交给系统下载管理器后丢失任务 ID。
- 下载任务、部分文件和完整 APK 分别保存在私有 SharedPreferences、`filesDir/app_updates`。进程退出后可恢复；清理缓存不会删除这些文件。设置 → 关于 → 更新下载始终保留当前任务入口，不依赖再次查询到新版本，也不依赖通知权限。清除应用数据或卸载仍会删除文件。
- 网络中断保留进度，最多自动重试两次；用户可手动继续。支持 HTTP Range；服务器忽略 Range 时重新下载，返回错误的范围时拒绝拼接。失败时在软件中保留原因，通知可返回任务；也提供浏览器下载入口。
- 完整文件检查大小、GitHub 提供的 SHA-256（存在时）、APK 包名、版本、渠道和签名，再标记为可安装。安装前重新检查。仅接受已知仓库 HTTPS 链接及 GitHub 资产 CDN 的有限跳转。
- 弹窗留在前台时，完成后打开系统安装界面；收起后通过完成通知或“更新下载”中的“安装更新”进入。未授予“安装未知应用”权限时先进入系统设置，授权返回后继续。不会在后台突然弹出安装器，也没有静默安装或强制更新。

这次调整解决任务和安装入口丢失、重试从头开始等流程问题。下载源仍为 GitHub Releases，没有增加第三方代理或服务器；速度仍取决于网络线路和包体积，不能保证和录屏中约 5 MB 的应用一样几秒完成。

旧版仍检查旧作者仓库，无法靠这次代码远程改变。第一次升级需手动安装新包，后续再通过新更新源提醒。

## 准备下一次更新

目标更新源为公开仓库 `yaselli/watermelon-chat` 的 GitHub Releases；兼容版在新地址返回 404 时回退到旧名 `yaselli/orangechat`，并且仅允许这两个仓库的 APK 下载地址。无需在 App 中保存 GitHub 令牌。仅 Actions 附件、草稿或无匹配 APK 的 Release 不会产生更新提醒。

仓库重命名是 GitHub 管理操作，修改代码里的地址不会自动重命名仓库。已经安装的旧版不能被远程修改：
`2.3.2 / 167` 只接受旧仓库名的下载 URL，即使 GitHub 将 API 请求重定向到新仓库，它仍会过滤新 URL。
仓库现已迁移，尚未安装兼容版的用户应手动下载 `2.3.3` 或对应 Debug 包，使用原渠道覆盖安装一次。
兼容代码同时校验新旧仓库的下载链接，但不承诺修复尚未升级的安装包。

当前 `2.3.6` 发布计划已由用户确认：本轮将全局外观、日常聊天、面板修正与缓存请求诊断合并发布。两条构建分别执行完整自动检查，正式版构建同时运行材质、导航背景和消息菜单界面回归，使用原渠道签名生成新 APK；发布任务核对已接受的源提交、版本、渠道、Tag 与全部附件校验和后公开。`verifiedRuns` 均为 0，不跳过检查，也不复用旧版本安装包。缓存请求诊断在两个渠道均有默认关闭的手动开关，只记录本机差异摘要，不增加模型请求，不代表服务端命中率已经修复。其他 Debug 专用面板继续隐藏于正式版。自动测试不能替代所有设备和真实模型的端到端体验验证。

没有已确认发布计划时，可使用以下草稿流程：

1. 从同一提交完成两条构建。构建脚本从 APK 实际包名、版本、debug 标记和 ABI 生成安装包文件名与 `release-metadata.json`，上传到既有 Actions 附件。
2. 将已通过验证的功能 PR 合入 `build/stable-release` 后，仅从该正式版分支运行 `release.yml`（Prepare Update Release），填写已成功的构建 run ID、`release` 或 `debug` 渠道，以及更新说明。可以复用已成功、且源提交已随 PR 合入维护分支的构建附件；应核对合并前后源树一致。工作流会核对构建来源、版本和 APK 校验和，再创建草稿。不要使用旧 `master` 的发布脚本；无需向 `master` 合入任何修改。
3. 在 GitHub Releases 检查草稿、安装包和更新说明后，手动发布。Debug 草稿自动标记 prerelease；正式版草稿不标记 prerelease。发布后 App 在下一次有效检查时提示更新。

通过 CLI 明确指定正式版分支：`gh workflow run release.yml --ref build/stable-release -f run_id=构建ID -f channel=release -f notes='更新说明'`。工作流增加分支校验，仅允许在 `build/stable-release` 执行。正式版分支今后每次更新会同时触发 Release 和 Debug 构建。

文件名约定由脚本统一生成，例如 `Xiguaban-2.3.1-166-arm64-v8a-release.apk`。不要手工改掉版本、渠道或架构。草稿创建不会自动公开，也不覆盖已有 Release。

发布完成与否以 GitHub Releases 的公开状态为准。完整安装仍需手机验证；签名必须沿用原渠道，否则 Android 无法覆盖安装。


## 当前下载改动的验证范围

- JVM：模拟完整下载、Range 续传、忽略 Range、响应体中断后续传、短响应、非法范围、跳转白名单、过大文件、错误摘要；校验包名/渠道/版本/签名策略，以及 Release 选择中大小和摘要的保留。
- Android 模拟器（由 Debug CI 执行）：任务和部分文件在 Store 重建后仍存在、暂停状态持久化、FileProvider 可读；实际安装 APK 与归档解析得到一致的包/渠道/签名身份。
- 尚未完成全面真机覆盖的场景：下载弹窗收起/重开应用、断网/恢复、关闭通知、未知来源授权后返回、完成通知入口，以及两种原渠道签名的覆盖安装。本次按自动回归结果发布，不宣称这些场景已经全部完成真机验收。


归档渠道读取的模拟器回归：Android 15 上同一 APK 的安装态 `ApplicationInfo.flags` 含 Debug 标记，`getPackageArchiveInfo` 返回的归档标记却未包含该位。归档渠道因此改为从该 APK 的二进制 AndroidManifest 读取 `android:debuggable`（支持资源布尔值），签名、包名和版本仍由 PackageManager 解析并按原规则严格匹配，不放宽渠道校验。模拟器测试比较同一实际 APK 的安装态与归档身份，并拒绝无法解析的文件。
